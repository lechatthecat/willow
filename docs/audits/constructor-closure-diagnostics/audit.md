# Constructor closure type diagnostics

Validated on Linux x86_64, 2026-10-26.

## Behavior and cause

A nominal type substituted into a generic constructor signature is carried by
an internal alias. The context-free type formatter printed that alias; emission
removed its hash and left `$type`. Constructor mismatch messages and primary
labels now resolve nominal aliases through the checker's existing map before
formatting. The expected spelling is computed once for both message and label.
Type compatibility, error code E0201, spans, inference, and function/closure
conversion rules are unchanged. This fix covers constructor value mismatches;
it does not globally rewrite diagnostic text or alter reference-argument errors.

The regression test failed before the fix with an internal alias in both the
expected closure parameters and label. Afterward the checked-in `repro.wi`
produces exactly one E0201 with `closure(Item, Item) -> bool` expected and
`fn(Item, Item) -> bool` found, in human and NDJSON output (exit 1 expected).

## Validation

- `cargo fmt --all -- --check`: passed.
- `cargo clippy --workspace --all-targets -- -D warnings`: passed.
- `cargo test --lib constructor_closure_diagnostic -- --nocapture`: two tests passed.
- `cargo test --lib generic_diagnostic_class_name_index_scaling -- --nocapture`: passed.
- `cargo build --bin willow`: passed.
- `target/debug/willow check docs/audits/constructor-closure-diagnostics/repro.wi`
  and the same command with `--format ndjson`: expected E0201, correct names and label.
- `target/debug/willow run example/constructor_closure_types.wi`: printed `true`.

The regression matrix has 20 explicit perspectives: each of Item, i64, bool,
String, and Array<Item>, crossed with implicit/memberwise versus explicit
constructors and repeated parameter positions versus return position. Every
case asserts the expected type, found type, primary label, E0201, and absence
of internal placeholders. The CLI reproduction additionally exercises a named
function argument; the runnable example exercises an accepted closure argument.

Full local suites and the full example audit were deliberately omitted. CI was
not queried. macOS arm64/x86_64 and Windows native execution are unverified.
Cross-target Clippy is not applicable to this compiler-only formatting change:
no platform APIs, cfg branches, runtime, linking, filesystem, or threading code
changed.

## Implementation and complexity audit

Reviewed the alias creation in generic binding preparation, constructor
argument checking and compatibility branch, type formatting, and diagnostic
emission. The existing alias map resolves nominal identities directly without
scanning templates, classes, or registry entries. Ordinary type_name callers
use the identity resolver and retain their prior behavior. The explicit work
stack is retained; no recursive tree clone or second formatting traversal is
introduced. No backend or generated-code/runtime behavior changes.

Let V be type-tree nodes, B rendered bytes, H total bytes hashed in nominal
lookup keys, and D emitted constructor mismatches. Formatting takes O(V+B+H)
expected time with hash-map lookup and O(V+B) worst-case scratch/output space.
Across diagnostics it sums over their respective types, rather than multiplying
by the number of registered aliases/templates. Writing B bytes is unavoidable.
The expected string is shared by the message and label construction; both output
copies remain required by the diagnostic representation.

Deterministic measured name-resolver counts for repeated identical aliases:

| Closure parameters | Name lookups | Rendered bytes |
| ---: | ---: | ---: |
| 1 | 1 | 21 |
| 16 | 16 | 111 |
| 256 | 256 | 1551 |

The scaling unit test asserts these counts and lengths. Complexity beyond these
measured shapes is inferred from the unchanged iterative traversal and single
lookup per name, not from wall-clock timings. No additional runtime allocations,
IR, or machine code are generated by the change. No unresolved finding within
this change's scope remains.
